M0 — 導入

データはもう RDF になっている

UniProt も PDB も ChEMBL も Reactome も、SPARQL で機械的に検索できます。

理屈のうえでは、「ヒトのライソゾーム酵素のうち承認薬の標的になっているもの」は 1 本のクエリで答えが出るはずです。

実際にはそうなっていません。

M0 — 導入

理由は3つ

1. 書ける人が少ない

能力の問題ではありません。年に数回しか書かないものを習得し続けるのは、投資として合理的ではないというだけです。

2. DB ごとに違う

UniProt では up:Protein。PDB では pdbo:datablock から辿る。1つ覚えても次で使えません。

3. 癖を知らないと書けない

どのグラフを指定するか、どの述語が速いか、どこで壊れるか。文書化されていないことが多い。

そして失敗が静かです。エラーではなく、間違った件数が返ってきます。

M3 — 下ごしらえ

RDF とは
「A の B は C」の山

   主語            述語           目的語
    │               │               │
    ▼               ▼               ▼
インスリン ──── 生物種 ─────────→  ヒト
    │
    ├──────── 長さ ─────────────→  110
    └──────── 関連疾患 ─────────→ 糖尿病

この3つ組を トリプル、真ん中を 述語と呼びます。どの述語が使えるかはデータベースごとに違う ── これがこの章の主題です。

SPARQL は、このトリプルへの問い合わせ言語。表に対する SQL にあたります。

「件数」とは、条件に合うトリプルの組み合わせが何通り見つかったかです。この章の後半で効いてきます。

M3 — 下ごしらえ

IRI とグラフ

<http://purl.uniprot.org/uniprot/P01308>          ← 主語（インスリン）
    <http://purl.uniprot.org/core/organism>       ← 述語（生物種）
        <http://purl.uniprot.org/taxonomy/9606> . ← 目的語（ヒト）

この URL の形をした名前が IRI。リンクに見えますが、役目は名前です。開けるものもありますが、それが目的ではなく、同じものを世界中で同じ名前で呼ぶためにあります。

エンドポイント (sparql.uniprot.org)
 ├─ グラフ <.../uniprot>        ← UniProt 本体のトリプル
 ├─ グラフ <.../taxonomy>       ← 生物種のトリプル
 └─ グラフ <.../別データセット>   ← 同居している別のもの

FROM <グラフ名> と書くとその仕切りの中だけを見ます。書かないと全部の仕切りをまたいで探します。

「細かい話だろう」と思うかもしれません。この章の後半で、それが間違いであることを実演します。

M3 — 核心

MIE ファイル

なぜ AI が、教わってもいないデータベースに正しい SPARQL を書けるのか。
説明書を渡しているからです。

設計目標：LLM が初回で正しく速い SPARQL を書けるだけの情報を、過不足なく与える。

全スキーマを渡せば正確だが巨大すぎる。概要だけでは書けない。
MIE は「モデルが自力で復元できないことだけ」を載せる。

M3 — MIE の中身

検証済みの実行例が原子単位

examples:
  - id: sequence_mass
    sparql: |
      SELECT ?isoform ?sequence ?mass
      FROM <http://sparql.uniprot.org/uniprot>
      WHERE { uniprot:P01308 up:sequence ?isoform .
              ?isoform a up:Simple_Sequence ;
                       rdf:value ?sequence ; up:mass ?mass .
              FILTER(STRSTARTS(STR(?isoform), ".../isoforms/P01308-")) }
    verified: {row_count: 1, date: "2026-09-14"}
    traps_avoided:
      - say: canonical を isoforms/ACC-1 と決め打ちしない
             （-1 以外が canonical のエントリが 782 件）
        check: {kind: count, expect: 782}

1つの例が3役を同時に果たす ── ①スキーマの形 ／ ②サンプルデータ ／ ③このDB特有の罠

罠の記述には check: が付き、主張そのものが実データで定期的に再検証されます。

M3 — なぜ先に読むのか

理由は2つ

1. 存在しない述語を書いても
エラーは出ない

ゼロ件が返ります。そして AI は「該当なし」と報告しがちです。検出が非常に困難です。

2.10（2026-08-29）から、空の結果にはサーバが「本当にないのか、クエリが違うのか」の注記を付けます。ただし注記であってエラーではありません。

2. 速さは
正しさの証拠にならない

ガイドが示す速さの目安：

特定の IRI 指定   ≫  FILTER(CONTAINS(...))
     速い                    遅い

実測：インスリンの配列を FILTER(CONTAINS) で取るクエリ（OPTIONAL を2つ足した形）は、8月は60秒でタイムアウト、10月は10秒で返った。ただしグラフ固定なしで219,436行。FROM で固定しても918行（欲しいのは1行）。

「遅いはずの形」が速く返っても、行数が正しいとは限りません。実行時間はキャッシュの状態でも変わります（行数は 2026-10-20）。

M3 — 静かな失敗

MIE を守ると、罠は
一度も発火しない

1つのエンドポイントに複数のデータセットが同居していると、グラフを指定しないクエリは全部を拾い、行数が黙って膨らみます。

対策は FROM <グラフ名> でグラフを固定すること。MIE がそう指示します。

つまり、黙って守っていると罠があったことすら分かりません。

→ わざと破ってみます。

M3 — わざと破った結果

行数は2倍。
しかし答えは合っている

UniProt のヒトのライソゾーム内腔酵素を数えるクエリを、 FROM 句でグラフを固定した版と、固定しない版の両方で実行して、 件数を比較して見せて。COUNT(*) と COUNT(DISTINCT) の両方を出して。
版COUNT(*)COUNT(DISTINCT ?protein)
FROM 固定あり9898
FROM 固定なし19698

最後の一文が重要です。これを付けないと、この罠は見えません。

（この実行は EC 番号で絞っていないので、98 はライソゾーム内腔のタンパク質の数。酵素に絞ると 52 で、M4 で使います）

10-20 の再実行では、モデルが EC 番号で絞り 62 / 124（DISTINCT は 52 / 52）。行数がちょうど2倍で DISTINCT は一致、という構図は同じでした。

M3 — この表の読み方

危ないのは
COUNT(*) のほう

「固定しないと答えが変わる」という話ではありません。

COUNT(DISTINCT) を使っている限り、この例では答えは合ってしまいます。両方とも 98 でした。

危ないのは COUNT(*) のほうで、196 という誤った数字が、エラーも警告もなく返ります。

さらに悪いことに、膨張率は固定ではありません。対象によって2倍になったりならなかったりします。

AVG／SUM を使う場合、あるいは両方のグラフにある述語を k 本つないで結合する場合（2k 倍）には、DISTINCT では吸収しきれず答えそのものが狂います。

M3 — 診断のしかた

出どころを突き止める

その2倍の行はどのグラフから来ているの？ GRAPH ?g で調べて。

GRAPH ?g は SPARQL の書き方で、「どのグラフ（仕切り）から来た行か」を ?g という空欄に入れて返させます。書けなくても、こう頼めば AI が書きます。

「タンパク質である」という情報を2つのグラフが供給していました：UniProt 自身と、同じエンドポイントに同居しているオーソログのデータベース OMA。

この診断のしかた自体を覚えてください。怪しい件数が出たら「どのグラフから来ているか、グラフごとに数えて」と頼む。そのまま実務で使えます。

M3 — 実測

COUNT(*) が実際に狂った例

62
COUNT(*)
52
COUNT(DISTINCT ?protein)
19%
差

1つのタンパク質が EC 番号を複数持っていたため（該当7個。GBA1 は4個、ASAH1 は3個）。
素朴に行数を数えていたら「ライソゾーム内腔酵素62個」と報告するところでした。正しくは52。

件数を報告する前に、COUNT(*) と COUNT(DISTINCT) を比べる。差があるなら、何が重複しているのか説明できるまで報告しない。

M5 — スキル

MCP と スキルの違い

MCP ＝ 能力

何ができるか。UniProt を引ける、SPARQL を投げられる、ID を変換できる。

Skill ＝ 方法論

どういう手順でやるか。どの順で、何を検証するか。

同じ道具でも、手順書があるかないかで結果の質が変わる ── さっき見たとおりです。

今日の「良い問い」と「検証」を、毎回手で書かなくて済むようにしたもの。

M7 — 検証の4手順

論文に使う数字は
例外なくこの4つ

  1. 実行されたクエリを全文出させて保存 ── 要約させない。これが実験ノートです
  2. COUNT で裏取り ── 差があるのは異常ではない。説明できないまま報告するのが異常
  3. 元のDBで1〜2件を目視 ── 30秒。上位1件より「意外な1件」を見る
  4. 実行日とエンドポイントを記録 ── いつ問い合わせたかがない結果は再現できません

M7 — 責任

向いていない用途

網羅性が要件の解析「すべての」を保証できません
統計的推論件数は返しますが、検定の設計はあなたの仕事です
臨床判断絶対に使わないでください。ClinVar の分類は診断でも助言でもありません

M9 — 演習

TogoVar：日本人集団のバリアント

GBA1 の病原性バリアントは何件？ そのうち日本人集団で頻度が高いものは？

M9 — 仕込み (1)(2)

227件 → 1件

(1) 「GBA」は完全一致しません。HGNC が GBA → GBA1 に改名済み。ID の解決は自明ではない。

(2) 病原性＋おそらく病原性の227件に、日本人集団での頻度条件（ToMMo でアレル頻度 0.05% 以上）を掛けると、残るのは rs421016（旧称 L444P）1件。この閾値の決め方は仕込み (4) で

コホートアレル頻度
ToMMo（日本人 n≈61,000）0.000785
NCBN（日本人）0.000807

gnomAD exomes の約9倍、gnomAD genomes の約3倍。国際DBだけを見ていたら見落とす情報です。

M9 — 仕込み (3) 集計単位の罠

内訳を足すと
総数を超える

内訳1つのバリアントが入る欄合計227 と比べて
type（SNV 191 / 欠失 31 / 挿入 5）ちょうど1つ（SNV・欠失・挿入のどれか）227✅ 一致
significance（Likely pathogenic 147 / Pathogenic 122 / ほか）複数のことがある：登録者・疾患ごとに別の分類が付く316❌ 約1.4倍
consequence複数のことがある：転写産物ごとに結果が違う827❌ 約3.6倍

各欄の数字は正しい。足すと誤りになる。「Pathogenic 122 ＋ Likely pathogenic 147 ＝ 病原性バリアント269個」と言えば誤りです。42個は両方に入っています。

しかも「病原性」で絞ったのに Uncertain significance が32件出てきます ── 1つのバリアントが、条件ごとに別の分類を持つから。ツール自身が「合計をバリアント数と比べるな」と警告を返してきます。

⚠️ ClinVar の疾患名は分類として述べること。リスクの助言ではありません。ヘテロ保因者はゴーシェ病を発症しませんが、無関係とも言えません（パーキンソン病との関連の報告があります）。

M8 — まとめ

3つだけ

  1. TogoMCP は SPARQL を投げる道具ではなく、どう投げるべきかの知識を配る仕組み。MIE ファイルが核心
  2. 失敗はエラーではなく、正しく見える数字として現れる。今日見たものは全部エラーが出ませんでした
  3. 裏取りしていない数字を論文に書かない。裏取り前の表のように、査読で聞かれたときに答えられません
