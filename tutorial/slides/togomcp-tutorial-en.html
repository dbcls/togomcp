Today’s goals

There are three

  1. Get connected and be able to use it
  2. Understand why it works — without this, you are helpless when it does not
  3. Be able to doubt an answer and verify it

What we spend the most time on today is not the examples that work, but the ones that do not.

M0 — Introduction

The data is already RDF

UniProt, PDB, ChEMBL, Reactome — all of them are machine-readably searchable with SPARQL.

In principle, “which human lysosomal enzymes are targets of approved drugs” should be answerable with a single query.

In practice it is not.

M0 — Introduction

Three reasons

1. Few can write it

Not a question of ability. It is simply not rational to keep up a skill you use a few times a year.

2. Every DB is different

In UniProt, up:Protein. In PDB you traverse from pdbo:datablock. Learning one gets you nothing for the next.

3. You need the quirks

Which graph to specify, which predicates are fast, where it breaks. Often undocumented.

And the failures are silent. Not an error — what comes back is the wrong count.

A standard for handing “tools” to an AI

    You    ──→  Claude, etc.  ──→  MCP server  ──→  external data

M3 — Groundwork

RDF is a pile of
“the B of A is C”

  subject         predicate         object
     │               │                 │
     ▼               ▼                 ▼
  insulin ──── organism ────────────→ human
     │
     ├──────── length ──────────────→ 110
     └──────── associated disease ──→ diabetes

These three parts are called a triple, and the middle one the predicate. Which predicates you can use differs from database to database — that is the subject of this chapter.

SPARQL is the query language for these triples. It is what SQL is to tables.

A “count” is how many combinations of triples match your conditions. That fact does the work later in this chapter.

M3 — Groundwork

IRIs and graphs

<http://purl.uniprot.org/uniprot/P01308>          ← subject   (insulin)
    <http://purl.uniprot.org/core/organism>       ← predicate (organism)
        <http://purl.uniprot.org/taxonomy/9606> . ← object    (human)

A name shaped like a URL is an IRI. It looks like a link, but its job is to be a name. Some do open in a browser, but that is not the point: it is there so that the same thing carries the same name everywhere in the world.

endpoint (sparql.uniprot.org)
 ├─ graph <.../uniprot>         ← UniProt's own triples
 ├─ graph <.../taxonomy>        ← organism triples
 └─ graph <.../another-dataset> ← something else living here

Writing FROM <graph> means look only inside that compartment. Leaving it out means search across all of them.

You may be thinking this is a mere detail. The second half of this chapter demonstrates that it is not.

M3 — The core

The MIE file

Why can an AI write correct SPARQL against a database nobody taught it?
Because we hand it the schema documentation.

Design goal: give the LLM exactly enough information to write correct, fast SPARQL on the first attempt — no more, no less.

The whole schema would be accurate but far too large. An outline alone is not enough to write with.
A MIE carries “only what the model cannot reconstruct on its own”.

M3 — Inside a MIE

A verified, executable example is the atomic unit

examples:
  - id: sequence_mass
    sparql: |
      SELECT ?isoform ?sequence ?mass
      FROM <http://sparql.uniprot.org/uniprot>
      WHERE { uniprot:P01308 up:sequence ?isoform .
              ?isoform a up:Simple_Sequence ;
                       rdf:value ?sequence ; up:mass ?mass .
              FILTER(STRSTARTS(STR(?isoform), ".../isoforms/P01308-")) }
    verified: {row_count: 1, date: "2026-09-14"}
    traps_avoided:
      - say: Do not hard-code the canonical as isoforms/ACC-1
             (782 entries have a canonical other than -1)
        check: {kind: count, expect: 782}

A single example does three jobs at once — ① the shape of the schema / ② sample data / ③ the trap specific to this DB

Each trap carries a check:, so the claim itself is re-verified against the live data.

M3 — Why read it first

Two reasons

1. A nonexistent predicate
raises no error

It returns 0 rows. And the AI tends to report “no matches.” This is extremely hard to detect.

Since 2.10 (2026-08-29) the server annotates an empty result: “genuinely absent, or a wrong query?” But it is a note, not an error.

2. Speed is
not evidence of correctness

The guide’s rule of thumb for speed:

specific IRI   ≫  FILTER(CONTAINS(...))
    fast                  slow

Measured: a query fetching insulin’s sequence with FILTER(CONTAINS) (plus two OPTIONALs) timed out at 60 s in August, and in October returned in 10 s, but with no graph pin it gave 219,436 rows. Pinned with FROM it still gave 918 rows (the answer is 1 row).

A “slow” shape coming back fast says nothing about the row count. Runtime also depends on the state of the cache (row counts: 2026-10-20).

M3 — Silent failure

Follow the MIE and
the trap never fires

When several datasets live side by side at one endpoint, a query that does not specify a graph picks up all of them, and the row count inflates silently.

The countermeasure is to pin the graph with FROM <graph name>. The MIE instructs exactly that.

Which means that if you quietly obey, you will never even learn the trap was there.

→ So let us break the rule on purpose.

M3 — Breaking it on purpose

The rows doubled —
but the answer is right

Take a query that counts human lysosomal lumen enzymes in UniProt and run it both ways — one version with the graph pinned in a FROM clause, one without — then compare the counts. Give both COUNT(*) and COUNT(DISTINCT).
VersionCOUNT(*)COUNT(DISTINCT ?protein)
FROM pinned9898
FROM not pinned19698

That last sentence matters. Without it, this trap stays invisible.

(This run did not filter on EC numbers, so 98 counts lysosomal lumen proteins. Restricted to enzymes it is 52, which M4 uses.)

On the 10-20 re-run the model filtered on EC numbers: 62 / 124 (DISTINCT 52 / 52). Rows exactly doubled while DISTINCT matched: the same picture.

M3 — How to read that table

The dangerous one is COUNT(*)

This is not the story of “leave the graph unpinned and the answer changes.”

As long as you use COUNT(DISTINCT), the answer in this example comes out right anyway. Both were 98.

The dangerous one is COUNT(*): the wrong number, 196, comes back with no error and no warning.

Worse, the inflation factor is not fixed — depending on the target it may or may not be 2×.

With AVG / SUM, or a join across k predicates that both graphs declare (2k×), DISTINCT cannot absorb it and the answer itself goes wrong.

M3 — How to diagnose

Track down where it came from

Which graph are those doubled rows coming from? Check with GRAPH ?g.

GRAPH ?g is SPARQL for “tell me which graph (compartment) each row came from”, returned in the blank ?g. You do not need to write it; ask like this and the AI writes it.

The fact “this is a protein” was supplied by two graphs: UniProt itself, and the ortholog database OMA, co-resident at the same endpoint.

Learn this diagnostic move itself. When a count looks suspicious, ask: “which graph is this coming from? Count per graph.” It transfers directly to real work.

M3 — Measured

Where COUNT(*) really went wrong

Because a single protein carries several EC numbers (7 proteins affected: GBA1 has 4, ASAH1 has 3).
Naively counting rows, you would have reported “62 lysosomal lumen enzymes.” The correct figure is 52.

M4 — Caveats to state

Just three

  1. Filter by IRI. We use EC-number and taxon IRIs, not title keywords. Filtering by string both misses things and lets the wrong ones in
  2. Resolution is X-ray only. Cryo-EM lives in a different field. This is not a ranking across mixed methods
  3. This result moves. If a 1.1 Å structure is deposited tomorrow, the ranking changes

So save the query, not the table.

M4 — None of them is the intent

Every definition lets in
things the intent excludes

The intent is “enzymes that work inside the lysosome.” Seen from there:

  • KW-0458: INSR / mTOR / PCSK9 / LRRK2 / PSEN2, plus ten RAB GTPases (they only pass through the lysosome)
  • GO:0043202: PDGFRB (a receptor tyrosine kinase), HSP90AA1 and HSPA8 (chaperones), GYG1 (glycogenin)

Narrowing by EC number to hydrolases does not fix it. With KW-0458, 114 of the 161 survive. RAB GTPases are EC 3.6.5.2, and HSP90AA1 and HSPA8 are EC 3.6.4.10 hydrolases too.

Each answer fits the words, so it does not look wrong. Only against the intent does it look strange.

M5 — Skills

The difference between MCP and skills

MCP = capability

What can be done. Look something up in UniProt, send a SPARQL query, convert an ID.

Skill = methodology

By what procedure. In what order, and what to verify.

Same tools, but the quality of the result changes with whether there is a written procedure — exactly what we just saw.

Today’s “good question” and “verification”, packaged so you never write them out by hand again.

Do not put an unverified number into a manuscript. The first table (TP53 at 1,581) was one. You will not be able to answer for it at review.

M7 — Verification and reproducibility

Not one of today’s failures
raised an error

  • Inflated counts (62 vs 52)
  • Sampling bias (MTOR 20th → 9th)
  • A definition chosen without your intent (the AI picks silently)
  • Misunderstanding the metric (co-occurrence ≠ causation)

They come back as plausible numbers.

M7 — The four verification steps

For any number that goes in a paper,
these four, without exception

  1. Make it output the executed query in full, and save it — do not let it summarize. This is your lab notebook
  2. Cross-check with COUNT — a difference is not an anomaly. Reporting it without being able to explain it is the anomaly
  3. Check one or two entries by eye in the source DB — 30 seconds. Look at “the surprising one” rather than the top hit
  4. Record the date of execution and the endpoint — a result with no “when” cannot be reproduced

M7 — Responsibility

What it is not good for

Analyses where completeness is a requirement“All of them” cannot be guaranteed
Statistical inferenceIt returns counts, but designing the test is your job
Clinical decisionsNever use it for this. ClinVar’s classifications are neither a diagnosis nor advice
Producing primary dataIt only queries existing DBs. It makes no new measurements

Cite at two levels — both TogoMCP and each database you actually used. TogoMCP is the entrance; it is not where the data came from.

M9 — Exercise

TogoVar: variants in the Japanese population

How many pathogenic variants are there in GBA1? Which of them are frequent in the Japanese population?

⏱ measured about 35–40 s / REST only, no SPARQL

Four things are built into it.

M9 — Built in (1)(2)

227 variants → 1

(1) “GBA” is not an exact match. HGNC has already renamed GBA → GBA1. Resolving an ID is not trivial.

(2) Filter the 227 (likely) pathogenic variants by Japanese frequency (ToMMo AF ≥ 0.05%): one is left, rs421016 (formerly L444P). Where that threshold comes from is item (4)

CohortAllele frequency

About 9× gnomAD exomes, about 3× gnomAD genomes. Information you would miss looking at international DBs alone.

⚠️ The Japanese cohorts’ values carry quality flags (GBA1 is highly similar to its pseudogene GBAP1). Part of the frequency difference may be a technical false positive.

M9 — Built in (3) The unit-of-aggregation trap

The breakdowns add up to
more than the total

BreakdownBins one variant falls intoTotalAgainst 227
type (SNV 191 / deletion 31 / insertion 5)exactly one (SNV, deletion or insertion)227✅ equal
significance (LP 147 / P 122 / others)possibly several: classified per submitter and condition316❌ 1.4×

Every number is right on its own. Adding them is what goes wrong. Say “Pathogenic 122 + Likely pathogenic 147 = 269 pathogenic variants” and you are wrong: 42 are in both.

And although we filtered on “pathogenic”, 32 Uncertain significance come back — because one variant carries different classifications for different conditions. The tool itself warns: do not compare the sum with the variant count.

⚠️ State ClinVar’s disease names as a classification. They are not advice about risk. Heterozygous carriers do not develop Gaucher disease, but that is not the same as unaffected (associations with Parkinson’s disease have been reported).

M8 — Summary

Just three

  1. TogoMCP is not a tool for sending SPARQL; it is machinery for distributing the knowledge of how to send it. The MIE files are the core
  2. Failure shows up not as an error, but as a number that looks correct. Nothing we saw today raised an error
  3. Do not put an unverified number into a manuscript. Like the first, unchecked table, you could not answer for it at review
