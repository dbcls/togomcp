# 05. スキルを使ったワークフロー

## MCP と スキルの違い

ここまで扱ってきた MCP は **「能力」** です ── 何ができるか。UniProt を引ける、SPARQL を投げられる、ID を変換できる。

**スキル**は **「方法論」** です ── どういう手順でやるか。

同じ道具を持っていても、手順書があるかないかで結果の質は変わります。これは[第 4 章](04-advanced-queries.md)で見たとおりです。同じツール群を使いながら、曖昧な問いは 12 秒でデータベースを参照せずに答え、仕様化した問いは自分の誤りを発見しました。**その差を再現可能な形でパッケージ化したもの**がスキルです。

```
MCP  = 道具箱（何ができるか）
Skill = 手順書（どう使うか、どの順で、何を検証するか）
```

スキルは、この教材の第 6 章・第 7 章でやってきたことを、**毎回手で書かなくて済むようにしたもの**と考えてください。

## 4 つのスキル

TogoMCP サーバは、以下のスキルを提供しています（サーバ上では*ワークフロー*と呼びます）。

> **入手先:** 入手は不要です。接続に含まれています。TogoMCP に接続したクライアント（Claude、ChatGPT、Gemini など）なら、インストールなしで使えます。Usage Guide に一覧があり、モデルが必要なものを `get_workflow` ツールで取得します。サーバ上の版が常に最新なので、修正も何もせずに届きます。
>
> 手元に置くのは任意です。Claude Code でスキルを自動で起動させたい場合は、https://github.com/dbcls/togomcp の `togo_mcp/data/skills/public/` 以下にあるスキルのディレクトリを `~/.claude/skills/<名前>/` に置いてください。手元の版とサーバの版が食い違った場合は、サーバの版が優先されます。
>
> ChatGPT の注意：ChatGPT はコネクタ追加時のツール一覧を使い続けます。一覧に `get_workflow` がなければ、コネクタの更新が必要です（第 1 章参照）。

### research-article-analysis — 論文の主張をデータベースで検証する

**何をするか:** 論文を渡すと、その本文を信じずに、主張を 1 つずつデータベースに照合します。

分子式、反応式、パスウェイ、タンパク質の機能、GO の定義 ── それぞれについて **ChEBI → Rhea → UniProt → Reactome → GO** という証拠チェーンを構築し、主張ごとに検証結果を返します。

**なぜ効くか:** キーワード検索で得られる断片（「この論文にはこう書いてある」）ではなく、**独立した典拠**に当てるからです。論文の記述が正しいかどうかは、その論文の中を読んでも分かりません。

**使いどころ:** 査読、追試の前の下調べ、引用しようとしている論文の確認、自分の原稿の事実確認。

```
この論文の生物学的な主張をデータベースで検証して。
（PDF を添付、または DOI / PMID を指定）
```

### disease-analysis — 疾患を多階層でマッピングする

**何をするか:** 1 つの疾患を、**分子 → 経路 → 細胞 → 組織 → 臨床 → 治療**の各階層に分けて記述します。TogoMCP に加えて TogoID・OLS4・PubMed を組み合わせます。

**なぜ効くか:** 疾患の情報は階層ごとに別のデータベースに散っています。分子欠損は UniProt、経路は Reactome、表現型は HP、疾患概念は MONDO/MeSH、治療は ChEMBL。**手で繋ぐと半日かかる**作業です。

**使いどころ:** 馴染みのない疾患を短時間で把握する、研究計画の初期調査、共同研究の相手の分野を理解する。

```
ファブリー病の病態を分子レベルから臨床症状まで多階層で分析して。
```

### PRISM — 複数の条件の交差を取る

**何をするか:** 「A でもあり B でもある」エンティティを見つけます。名前は **P**redicate-defined, **R**eproducible, **I**dentifier-bridged, **S**et-intersection **M**ining の頭文字。

- 「疾患 X に関連し、かつ創薬可能な標的」
- 「経路 P に関与し、かつ既存薬で調節されている遺伝子」
- 「表現型 Q に関連し、かつ酵素 A の基質でもある化合物」

**なぜ効くか、そして最も重要な点:** PRISM は各条件（軸）を、**再現可能な述語として定義することを強制**します。オントロジーの階層に沿って展開し、複数の証拠源で三角測量し、安定した ID で交差を取り、**provenance ledger（典拠台帳）を残します**。

これは[第 7 章](07-verification.md)の検証 4 手順を、自動で、漏れなくやるための仕組みです。

> スキルの説明文に、こういう一文があります ──
> **「候補遺伝子を記憶から挙げそうになったら、止めて PRISM を使え」**
>
> [第 4 章](04-advanced-queries.md)の失敗デモそのものです。

**使いどころ:** ドラッグリポジショニング、創薬標的の同定、「この 2 つの集合に共通するものは？」型の問い。

```
◯◯病に関連し、かつ既存の承認薬で調節可能な遺伝子を PRISM で探して。
```

実績のある適用例として、加齢黄斑変性の脂質輸送、ポンペ病の解析があります。

### query-provenance — 結論の裏にある問い合わせを記録し、論文用にまとめる

**何をするか:** 調査の結論ごとに、それを支えるツール呼び出し（SPARQL、`search_*`、TogoID、NCBI、TogoVar）を**送ったとおりの文字列で**記録し、もう一度実行して同じ結果が返ることを確かめ、論文用に 3 つのファイルにまとめます。

```
ledger.yaml     問い合わせ台帳。呼び出しと引数、観測した結果、再実行での照合結果
PROVENANCE.md   人が読む版。主張ごとに、支えるクエリの全文と照合結果、再実行の方法
METHODS.md      方法欄の下書き。数字はすべて台帳から取る
```

**なぜ効くか:** **プロンプトは記録になりません。** 同じ質問文を投げても、LLM は同じ道筋をたどらないからです（[第 7 章](07-verification.md)）。再現できるのは、引数まで含めた**ツール呼び出しそのもの**です。このスキルはそれを、要約も書き直しもせずに写し取ります。照合は会話中の元の呼び出しではなく**台帳から写した引数で**再実行するので、写し間違いもここで見つかります。見えないもの（サーバのバージョン、結果のハッシュ）を作り出すこともしません。空欄のまま残し、後述の再実行スクリプトが埋めます。

**使いどころ:** 結果を論文・報告・発表に使うとき。[第 7 章](07-verification.md)の「クエリを残す」「日付とエンドポイントを記録する」を、手作業なしでやるための仕組みです。

**最初に言うのがコツです。** 調査の**始め**に宣言すると、呼び出しのたびにその場で台帳に書き込みます。後から頼んでも作れますが、長い会話では初めのほうのクエリの全文が文脈から消えていることがあり、そのぶんは「復元不能」として記録されます。

```
この調査の結果は論文に使うので、問い合わせを記録しながら進めて。
（続けて、いつもどおりの質問）
```

クライアントのプロンプト一覧から **Record this investigation for a paper**（`record_for_paper`）を選んでも同じことが起きます。Claude デスクトップはサーバの案内をモデルに渡さないので、**頼まない限りこのスキルは始まりません**。上のように一言添えるか、このプロンプトを使ってください。一覧に見当たらなければ、TogoMCP の接続をいったん外して繋ぎ直してください（クライアントは最初に接続したときのプロンプト一覧を使い続けます）。

**読者は台帳を自分で再実行できます。** 再実行スクリプトは SPARQL を TogoMCP を経由せずエンドポイントへ直接送るので、TogoMCP が変わっても、なくなっても動きます。

```bash
uv run https://raw.githubusercontent.com/dbcls/togomcp/v2.29.0/scripts/togomcp_reproduce.py ledger.yaml
```

> PRISM の「典拠台帳（provenance ledger）」とは別物です。PRISM のものは 1 回の交差の、メンバーごとの証拠表です。**組み合わせて使えます** ── 「PRISM で探して、問い合わせは query-provenance で記録して」。

## スキルを使うべきかの判断

| 状況 | 推奨 |
|---|---|
| 1 回きりの単純な問い合わせ | スキル不要。第 6 章のテンプレートで十分 |
| 同じ型の作業を繰り返す | **スキルを使う。**手順のばらつきが消える |
| 結果を論文に載せる | **query-provenance を使う。**問い合わせが記録され、再実行で確かめられ、方法欄の下書きまで出る |
| 手順そのものを共有・査読したい | **スキルを使う。**手順がファイルとして存在する |
| 探索的に手探りしたい | スキルは邪魔になることがある。素で聞く |

スキルの本質的な価値は、**あなたが疲れていても、急いでいても、同じ手順が踏まれること**です。第 4 章の失敗デモが示したように、手順を省くと 12 秒で答えが出てしまいます。そして省いたことは画面に表示されません。

## 自分でスキルを作る

スキルは Markdown ファイルです。`SKILL.md` に、いつ使うか（`description`）と、どういう手順で作業するかを書きます。

あなたの研究室に固有の手順 ── 「うちの解析では必ずこの 3 つの DB を当てて、この形式で表にする」── があるなら、それをスキルにできます。TogoMCP リポジトリの既存スキルが実例になります。
